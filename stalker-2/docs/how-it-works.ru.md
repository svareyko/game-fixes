# Как это нашли — вылет GPU в S.T.A.L.K.E.R. 2 при Async Compute

**Читай это, когда:** тебе нужны доказательства, на которых держится [README](../README.ru.md), ты хочешь проверить,
тот ли у тебя вылет, или хочешь копать дальше.

## 1. Как выглядит вылет

Игра 2.0.6 (Unreal Engine 5.5.4), драйвер NVIDIA 616.92, RTX 5090. Каждый вылет выглядел одинаково:

| Источник | Что показывает |
|---|---|
| Краш-репортёр, `CrashContext.runtime-xml` | `CrashType = GPUCrash`, `ErrorMessage = GPU Crash dump Triggered` |
| `Stalker2.log` | `GPU crash detected: Device 0 Removed: DXGI_ERROR_DEVICE_HUNG`; видеопамяти занято около 10 ГБ из бюджета 31 ГБ — это не случай нехватки памяти |
| Системный журнал событий | от трёх до пяти `nvlddmkm` Event ID 153 за ~10 с, затем `Display` Event ID 4101 (механизм Windows по обнаружению тайм-аутов и восстановлению, TDR, сбросил GPU) и отчёт `LiveKernelEvent 141` |
| Вылет на стороне CPU | нет: отчёт — это собственная реакция движка на потерю устройства, а не сбой в коде игры |

`DXGI_ERROR_DEVICE_HUNG` — лишь то, что Direct3D сообщает после того, как Windows уже сбросила GPU.
Причину сброса нужно искать в другом месте — в разделах 2 и 3.

| Когда | Секунд после запуска | Где |
|---|---|---|
| день 1 | 21 403 (≈ 6 ч) | Химзавод |
| день 2, три вылета за 18 минут | 568 · 271 · 248 | Свалка, Росток, Росток |
| день 3 | 126 · 138 | Росток, Росток (второй — вообще без торговли, во время Выброса) |

## 2. Дамп драйвера NVIDIA

После каждого такого сброса драйвер записывает `C:\ProgramData\NVIDIA Corporation\nvtopps\nct\NV_dmp_<N>.nv-gpudmp`
и небольшой `NV_dmp_<N>.json`. Слоты пронумерованы и заполнялись по порядку (`_0`, `_1`, … `_5`); движку
для этого никакие настройки не нужны.

`.nv-gpudmp` — это дамп сбоя NVIDIA Nsight Aftermath. Его можно расшифровать и без Nsight Graphics:
игра сама поставляет библиотеку Aftermath
(`Engine\Binaries\ThirdParty\NVIDIA\NVaftermath\Win64\GFSDK_Aftermath_Lib.x64.dll`), а её функции
`GFSDK_Aftermath_GpuCrashDump_CreateDecoder` / `…GenerateJSON` превращают дамп в JSON.

Все шесть дампов из этой игры одинаково описывают сбой:

| Поле | Значение |
|---|---|
| Состояние устройства | `Error_DMA_PageFault` — сбой адресации, а не тайм-аут |
| Виртуальный адрес GPU, вызвавший сбой | **`0`** |
| Тип сбоя MMU | «The MMU returned an unknown reason» |
| Сброс | сброшен движок GPU, адаптер целиком — нет |
| Маркеры событий | нет |

Сбойный шейдер — это **compute shader**, и он встречается в двух вариантах:

| Размер | Начальный адрес | Хеш в `.json` | Встречался |
|---|---|---|---|
| 57 856 байт | `0x200419c00` | `0xd3dec00000000001` | 3 раза здесь (драйвер 616.92); также дважды в Ready or Not (Unreal Engine 5.3.2) на драйверах 616.56 и 616.64 — `.json` совпадает байт в байт |
| 42 752 байта | `0x200474b00` | `0x00000000d3d55001` | 3 раза здесь, с двумя или тремя адресами trap в `.json` вместо одного |

Один и тот же шейдер по одному и тому же адресу GPU в двух разных играх и на трёх версиях драйвера не может
быть содержимым игры. Оба хеша выглядят синтетическими (`d3d…`), и оба шейдера лежат в самом начале кучи
шейдеров — скорее всего, это шейдеры самого драйвера, которые он запускает, обрабатывая команды игры.
Последнее — вывод, а не проверенный факт.

## 3. Что делал GPU (DRED)

Direct3D 12 Device Removed Extended Data записывает, какие команды какого списка команд GPU успел завершить.
Движок выводит это в `Stalker2.log`, когда задано `r.D3D12.DRED=1` (см. README).
Без этого в логе стоит `DRED: No command list found with active outstanding operations` — что означает лишь,
что ничего не отслеживалось, а не что ничего не выполнялось.

Два вылета при включённом DRED:

**Случай A** (шейдер 57 856 байт):

```
DRED: Commandlist "(null)" on CommandQueue "3D Queue (GPU 0)", 378 completed of 1084
    Op: 377, DrawIndexedInstanced - LAST COMPLETED
    Op: 378 … 398, DrawIndexedInstanced
DRED: No PageFault data.
```

Ни в одной другой очереди не было незавершённой работы.

**Случай B** (шейдер 42 752 байта), загрузка сохранения и прогулка по Ростоку:

```
DRED: Commandlist "(null)" on CommandQueue "3D Queue (GPU 0)", 594 completed of 1131
    Op: 593, ExecuteIndirect - LAST COMPLETED      (121 ExecuteIndirect in a row around it)
DRED: Commandlist "(null)" on CommandQueue "Compute Queue (GPU 0)", 1 completed of 9
    Op: 0, BeginCommandList - LAST COMPLETED
    Op: 1, Dispatch / 2, ResourceBarrier / 3, Dispatch / …
```

Графическая очередь остановилась посреди серии отрисовок `ExecuteIndirect`, а очередь async compute
начала свой список, но не завершила даже первый `Dispatch`.

## 4. Что это значит

1. **GPU остановился внутри собственных списков команд игры.** Не в другой программе, не в композиторе
   рабочего стола и не в DLSS Frame Generation — генерация кадров выполняется в момент показа кадра, а не как
   часть длинного списка отрисовок игры. Reflex и Frame Generation всё же могут влиять на тайминг.
2. **Чтение по нулевому адресу.** Compute shader — скорее всего, тот, который драйвер запускает от имени игры, —
   прочитал адрес GPU 0. `ExecuteIndirect` берёт свои аргументы, среди которых могут быть адреса GPU, из
   буфера, который GPU заполняет сам. Если этот буфер прочитан раньше, чем записан, адреса в нём нулевые.
3. **Случай B показывает именно такую пару:** графическая очередь потребляет аргументы `ExecuteIndirect`,
   очередь async compute производит работу. В Unreal Engine 5 именно это делает Nanite: при
   `r.Nanite.AsyncComputeMainPassCullingAndBinning` отсечение невидимого и раскладка по корзинам (culling и binning) основного прохода выполняются в очереди
   async compute и записывают indirect-аргументы, по которым затем рисует графическая очередь. Отсутствие или
   нарушение синхронизации между двумя очередями — в игре, движке или драйвере — привело бы к такому сбою.
4. **Почему помогает отключение Async Compute:** тогда вся вычислительная работа идёт в графической очереди,
   по порядку, и зависимость между очередями исчезает.

Пункты 2–4 — гипотеза, которая подходит к обоим случаям DRED; проход-виновник не доказан.

| Подозреваемый | Проверка | Результат |

| Видеопамять | memtest_vulkan 0.5.0, 16 мин, 25,4 из 32 ГБ, сразу после трёх вылетов | 0 ошибок |

## 6. Открытые вопросы

- **Какой именно проход.** Вариант `r.Nanite.AsyncComputeMainPassCullingAndBinning=0` из README подтвердил бы
  теорию про Nanite, если игра перестанет вылетать при включённом Async Compute.
- **Другие карты.** Наблюдалось на одной RTX 5090. Затронуты ли другие карты RTX 50, более старые карты или
  другие драйверы — неизвестно.
- **Не всё на этом ПК объяснено.** На той же машине было несколько сбросов драйвера, когда никакая игра не
  была запущена; дампов они не оставили, и этот разбор их не охватывает.
- **Собственный Aftermath движка** (`r.GPUCrashDebugging.Aftermath=1`) не включился в этой сборке игры
  (`RHI.Aftermath=false` в контексте краша), поэтому маркеров событий не было.

## 7. Как собрать те же данные

1. Добавь строки DRED из README в `%LOCALAPPDATA%\Stalker2\Saved\Config\Windows\Engine.ini` и
   сделай файл **только для чтения** — игра удаляет его, прочитав при запуске.
2. После вылета скопируй папку краша из `%LOCALAPPDATA%\Stalker2\Saved\Crashes\` и самый новый
   `NV_dmp_<N>.*` из `C:\ProgramData\NVIDIA Corporation\nvtopps\nct\`.
3. В папке краша `CrashContext.runtime-xml` теперь должен содержать `RHI.DRED = true` и
   `RHI.DREDHasBreadcrumbData = true`; строки `DRED:` — в конце `Stalker2.log` (UTF-16).
