# Как устроены Metal Torches

Заметки для мододелов: как собраны два маленьких блока под Minecraft 26.2 и в каких
местах игра сопротивлялась. Всё, что ниже сказано о ванильной игре, прочитано из самого
клиента 26.2 — из его файлов данных и дизассемблера, — а не из документации к старым
версиям.

*рецепт работает, но его нет в книге рецептов · advancement/recipes · recipe_unlocked ·
TorchBlock SimpleParticleType · WallTorchBlock codec · overrideLootTable · с настенного
факела ничего не выпадает · мод Fabric без Gradle и Loom · Minecraft 26 без обфускации*

**Читать, когда:** хочешь изменить мод, перенести его на другую версию игры или
позаимствовать один из приёмов.

## 1. Файлы

| Файл | Зачем |
|---|---|
| `src/metaltorch/MetalTorch.java` | перечисление металлов: id, цвет, ингредиент рецепта |
| `src/metaltorch/MetalTorchBlock.java` | напольный факел |
| `src/metaltorch/MetalWallTorchBlock.java` | настенный факел |
| `src/metaltorch/MetalTorchMod.java` | регистрирует блоки и предметы, наполняет творческую вкладку. Точка входа `main` |
| `resources/fabric.mod.json` | манифест мода, написан руками |
| `resources/assets`, `resources/data` | пишет генератор, руками не правятся |
| `tools/resources.py` | генератор: текстуры, модели, блокстейты, таблицы добычи, рецепты, достижения-разблокировки, языковые файлы |
| `tools/SelfTest.java` | проверка правила таблиц добычи на живых ванильных блоках, при каждой сборке |
| `tools/ValidateMod.java` | проверка `fabric.mod.json` собственным парсером Fabric Loader, при каждой сборке |
| `build.py` | сборка: classpath, `javac`, проверки, jar |

Четыре класса, ни миксинов, ни access widener, ни настроек.

## 2. Два блока, один предмет

Факел в Minecraft — это **два блока**: напольный и настенный, у которого есть свойство
`facing` и наклонённая модель. Мод повторяет это для каждого металла и регистрирует на
пару один предмет:

```java
Block standing = Registry.register(BuiltInRegistries.BLOCK, standingKey,
        new MetalTorchBlock(metal.colour(), torchProperties().setId(standingKey)));
Block wall = Registry.register(BuiltInRegistries.BLOCK, wallKey,
        new MetalWallTorchBlock(metal.colour(),
                torchProperties().overrideLootTable(standing.getLootTable()).setId(wallKey)));

Item item = Registry.register(BuiltInRegistries.ITEM, itemKey,
        new StandingAndWallBlockItem(standing, wall, Direction.DOWN,
                new Item.Properties().useBlockDescriptionPrefix().setId(itemKey)));
```

* `StandingAndWallBlockItem` — ванильный класс, на котором держится предмет «факел». Он
  сам решает, какой из двух блоков поставить, по грани, в которую щёлкнул игрок;
  `Direction.DOWN` говорит, что напольный вариант опирается на блок снизу.
* `useBlockDescriptionPrefix()` заставляет предмет брать название из ключа перевода
  блока, поэтому в языковых файлах лежат только ключи `block.metaltorch.*`.
* Оба класса наследуются от ванильных `TorchBlock` / `WallTorchBlock`. На чём факел может
  стоять, когда он отваливается и как ставится — всё это живёт в ванильных родителях и
  заново не пишется.
* Регистрация идёт в статическом инициализаторе класса точки входа, то есть происходит,
  когда Fabric загружает мод, — до заморозки реестров. `onInitialize()` только добавляет
  предметы на ванильную вкладку **«Функциональные блоки»** через Fabric API
  (`CreativeModeTabEvents.modifyOutputEvent`). Этот вызов и есть причина, по которой
  Fabric API в зависимостях.

Порядок значений в перечислении можно менять свободно: наружу уезжают имена блоков, а не
порядковые номера.

## 3. Уровень света 15 и никакого цвета

```java
BlockBehaviour.Properties.of().noCollision().instabreak().lightLevel(state -> 15).sound(SoundType.WOOD)
```

Движок хранит свет одним маленьким числом на позицию блока, 0..15. Канала для цвета нет,
поэтому блок может быть только *ярче*, но не *желтее*. У ванильного факела 14, а 15 —
верх шкалы: дальше моду идти некуда. Таблица уровней, прочитанная из живой игры, — в
[README](../README.ru.md#уровни-света).

Поэтому цвет металла (`0xF0F4F8` железо, `0xFFD24A` золото) уходит в два единственных
места, где его можно показать: в текстуру и в частицы.

## 4. Цветные искры

Очевидный план — отдать факелу цветную частицу пламени — не компилируется. Оба ванильных
конструктора требуют тип частицы *без параметров*:

```
protected TorchBlock(SimpleParticleType, BlockBehaviour.Properties)
protected WallTorchBlock(SimpleParticleType, BlockBehaviour.Properties)
```

Цветная частица — это `DustParticleOptions`, частица *с* параметрами, а не
`SimpleParticleType`. Поэтому мод передаёт ванильный `ParticleTypes.FLAME`, чтобы
удовлетворить конструктор, а затем полностью переопределяет `animateTick`, так что эта
частица не используется вовсе:

```java
level.addParticle(ParticleTypes.SMOKE, x, y, z, 0.0, 0.0, 0.0);
DustParticleOptions spark = new DustParticleOptions(colour, 0.7F);   // упакованный RGB, масштаб
for (int i = 0; i < 2; i++) {
    level.addParticle(spark,
            x + (random.nextDouble() - 0.5) * 0.12,
            y + random.nextDouble() * 0.12,
            z + (random.nextDouble() - 0.5) * 0.12,
            0.0, 0.0, 0.0);
}
```

Дым как у обычного факела плюс две искры-пылинки за такт анимации: одна выглядит бедно,
три уже мельтешат. **Ванильной частицы пламени нет совсем**: «пламя», которое ты видишь, —
это светлый верх текстуры плюс искры.

Где появляются частицы:

| Вариант | Положение |
|---|---|
| напольный | центр блока, `y + 0.7` — ванильные значения |
| настенный | `y + 0.7 + 0.22` и 0.27 от центра блока в сторону стены (`FACING.getOpposite()`) — ванильные значения, потому что модель — ванильная `template_torch_wall`. До 1.1.0 включительно `+ 0.22` не было, и искры начинались ниже кончика |

`emit(...)` — статический метод, общий для обоих классов блоков; настенный класс лишь
считает другое положение.

## 5. Загвоздка с кодеком

Каждый класс блока в 26.2 обязан вернуть свой `MapCodec`. Два ванильных родителя
объявляют этот метод по-разному:

```
TorchBlock:      public MapCodec<? extends TorchBlock> codec()
WallTorchBlock:  public MapCodec<WallTorchBlock>       codec()     // инвариантно
```

С `? extends` подкласс может сузить возвращаемый тип до `MapCodec<MetalTorchBlock>`. С
инвариантным объявлением — нет, компилятор отказывает. Отсюда разница между двумя почти
одинаковыми классами: `MetalWallTorchBlock.CODEC` типизирован **родителем**
(`MapCodec<WallTorchBlock>`), а в его геттере и в лямбде конструктора стоят приведения.

Оба кодека хранят цвет рядом со свойствами блока (`Codec.INT.fieldOf("colour")`), так что
экземпляр можно восстановить из данных.

## 6. Настенный факел и его добыча

Самое опасное место в моде: ошибись здесь — и с факела, сломанного на стене, **не выпадет
ничего**. Ни вылета, ни намёка на причину.

У настенного факела **нет своего файла таблицы добычи**. Он ссылается на таблицу
напольного. Ваниль делает ровно так же. В клиентском jar есть
`data/minecraft/loot_table/blocks/torch.json` и нет `wall_torch.json`, а дизассемблер
`net.minecraft.world.level.block.Blocks` показывает, как игра собирает собственные
настенные блоки: приватный помощник `wallVariant(base, copyName)` начинает свойства с
`overrideLootTable(base.getLootTable())` и, если попросили, заодно копирует название через
`overrideDescription(base.getDescriptionId())`.

Мод делает первую половину руками: `overrideLootTable(standing.getLootTable())`.
Название он не копирует — у настенного блока свой ключ в языковых файлах.

А откуда берётся таблица напольного факела? `Properties.setId(key)` ставит **только id**;
ключ таблицы добычи выводится из него как `<namespace>:blocks/<id блока>`. Отсюда место
файлов:

```
data/metaltorch/loot_table/blocks/iron_torch.json
data/metaltorch/loot_table/blocks/gold_torch.json
```

Это правило не вычитано из байт-кода с надеждой на лучшее. **Каждая сборка проверяет его
на живых ванильных блоках**: `tools/SelfTest.java` поднимает реестры игры
(`SharedConstants.tryDetectVersion()` + `Bootstrap.bootStrap()`, без окна и без OpenGL),
спрашивает у настоящих `Blocks.TORCH` и `Blocks.WALL_TORCH` ключи их таблиц добычи и
печатает:

```
ok   the vanilla torch has a loot table
vanilla torch      -> minecraft:blocks/torch
vanilla wall torch -> minecraft:blocks/torch          <- тот же ключ
ok   the key is derived as <namespace>:blocks/<block id>
ok   the wall torch points at the table of the standing torch - the scheme this mod repeats
```

Если обновление игры изменит правило, упадёт сборка, а не молча перестанут выпадать
факелы. Кроме того, сборка отказывается принимать лишний файл таблицы `*_wall_torch.json`:
он означал бы, что кто-то «починил» схему, не поняв её.

Собственных классов мода самотест не касается: загрузка `MetalTorchMod` попыталась бы
регистрировать блоки в уже замороженные реестры.

## 7. Рецепт, которого не было в книге рецептов

**Симптом.** В первой версии мода был файл рецепта — и больше ничего. Рецепт загружался и
**работал**: выложи предметы в сетку руками, и факелы получатся. Но книга рецептов его не
показывала. Лог при этом был совершенно чистым: ни ошибки, ни предупреждения, датапак
загрузился, а строка `Loaded N recipes` даже выросла на число новых рецептов.

**Причина.** Книга рецептов показывает только **разблокированные** рецепты, а
разблокирует рецепт отдельный файл-*достижение*. У ванили такой есть для каждого её
рецепта; у самого факела это `data/minecraft/advancement/recipes/decorations/torch.json`.

**Решение.** По одному достижению на рецепт в `data/<namespace>/advancement/recipes/`:

```json
{
  "parent": "minecraft:recipes/root",
  "criteria": {
    "has_ingredient": {
      "trigger": "minecraft:inventory_changed",
      "conditions": { "items": [ { "items": "minecraft:iron_ingot" } ] }
    },
    "has_the_recipe": {
      "trigger": "minecraft:recipe_unlocked",
      "conditions": { "recipe": "metaltorch:iron_torch" }
    }
  },
  "requirements": [ [ "has_the_recipe", "has_ingredient" ] ],
  "rewards": { "recipes": [ "metaltorch:iron_torch" ] }
}
```

Достаточно любого из двух критериев (один внутренний список = ИЛИ): игрок подобрал
ключевой ингредиент либо рецепт у него уже есть. Награда его и открывает. Подпапка
`decorations` повторяет место, где ваниль держит свой факел; это соглашение.

**Как распознать в следующий раз.** Сравни `Loaded N recipes` в логе с запуском без мода.
Число выросло — значит, рецепты разобрались, и дело в разблокировке, а не в JSON рецепта.

Сам рецепт бесформенный, `4 × minecraft:torch + 1 слиток → 4 факела`, категория `misc`.
Сборка теперь отказывается выпускать jar, в котором у металла есть рецепт, но нет файла
разблокировки.

## 8. Ресурсы генерируются

Двум металлам нужно **22 файла**: на металл — текстура, две модели блока, два блокстейта,
модель предмета, описание предмета, таблица добычи, рецепт и достижение-разблокировка,
плюс два языковых файла. Различаются они одним словом, а править такое руками — верный
способ завести опечатку. Все их пишет `tools/resources.py write`.

| Что | Как |
|---|---|
| модели | обёртки над ванильными шаблонами `minecraft:block/template_torch` и `template_torch_wall`. Своей геометрии у факела нет, меняется только текстура |
| блокстейт настенного | четыре поворота `facing` ванильного `wall_torch` (east 0, south 90, west 180, north 270) |
| текстура | 16×16, рисуется попиксельно через Pillow. Ванильный шаблон берёт только полосу x 7..9, y 6..16, поэтому всё рисуется строго в ней: палка, металлическое кольцо, пламя с оттенками от цвета металла (×0.55 на кольце до ×1.45 на кончике). Пиксели вне полосы были бы видны лишь на иконке предмета |
| предмет | `items/<id>.json` → `models/item/<id>.json` с родителем `minecraft:item/generated` и текстурой блока в `layer0` |
| языковые файлы | `block.metaltorch.<id>_torch` и `..._wall_torch` для английского и русского плюс `modmenu.descriptionTranslation.metaltorch`, чтобы Mod Menu показывал переведённое описание. Английское описание копируется из `fabric.mod.json` — его единственного дома |

Встроены две страховки:

* **Генератор сверяет себя с перечислением в Java.** Он разбирает `MetalTorch.java` и
  отказывается что-либо писать, если id, цвета или ингредиенты расходятся с его таблицей.
* **Генератор владеет своими каталогами** (`OWNED_DIRS`). Он пишет их целиком, а значит,
  и удаляет всё, чего в этот раз не написал. Без этого убранный металл оставляет свои
  файлы, и они молча уезжают в jar — так чуть не случилось, когда убирали медный факел.

Результат детерминирован: повторный запуск с той же версией Pillow переписывает каждый
файл байт в байт.

## 9. Сборка обычным javac

Gradle и Loom здесь нет, и это следствие устройства игры, а не вкуса.

**Почему так можно.** Minecraft 26.x поставляется **необфусцированной**: в клиентском jar
настоящие имена вроде `net.minecraft.world.level.block.TorchBlock`. Mojang перестала
публиковать маппинги начиная с 26.1, Yarn под 26.2 не выходил, а fabric-intermediary для
26.2 — пустая заглушка. Имена в исходниках — это имена в jar. Ремаппингу — главной работе
Loom — делать нечего, поэтому `javac` против установленной игры — это полноценная сборка,
и сеть ей не нужна.

**Что делает `build.py build`:**

1. **Classpath из манифеста профиля.** Список библиотек читается из манифеста версии
   профиля (`<имя>.json`), а **не** обходом папки `libraries`. В этой папке лежат jar и от
   других установок — по нескольку версий `authlib`, `datafixerupper` и `asm` бок о бок.
   Обойди её — и все они попадут в classpath, победителя выберет порядок файлов,
   компиляция при этом пройдёт, а самотест упадёт с `NoSuchMethodError` внутри ванильного
   кода. Манифест же перечисляет ровно те версии, с которыми игра стартует.
2. Библиотеки с правилами `rules` по ОС, которых нет на диске, пропускаются — это нативы
   для чужих операционных систем. Пропажа библиотеки *без* правил означает битую
   установку, и сборка останавливается.
3. Jar-файлы копируются в **один плоский каталог** во временной папке системы и
   передаются как `-cp каталог/*`: classpath, выписанный строкой, упирается в предел
   командной строки Windows в 32767 символов. Клиент копируется как `AAA-minecraft.jar`,
   чтобы сортироваться раньше библиотек с теми же пакетами.
4. Fabric API — это контейнер: настоящие модули лежат внутри него в `META-INF/jars/`. Они
   извлекаются в тот же каталог.
5. `javac --release 25 -proc:none -encoding UTF-8`, затем проверки из следующего раздела,
   затем обычный zip: `resources/` плюс классы.

**Чем за это заплачено.** Сборка зависит от того, как лаунчер раскладывает установку (см.
ограничение в [README](../README.ru.md#сборка-из-исходников)); нет ни управления
зависимостями, ни проекта для IDE; под каждую версию игры нужна пересборка против этой
версии. Для четырёх классов это хороший размен. Для большого мода — нет.

## 10. Что проверяет сборка

Сборка не заканчивается словами «скрипт отработал без ошибок» — она проверяет результат.

| Проверка | Что ловит |
|---|---|
| каждая ссылка на `net/minecraft/**` в скомпилированных классах (`javap -c`) существует в клиентском jar | компиляцию против чужой версии игры: в папке libraries может лежать другой клиент, и `javac` молча резолвит из него |
| `tools/SelfTest.java` на живых ванильных блоках | изменение правила таблиц добычи из раздела 6 |
| десять поимённых файлов на металл лежат в jar | забытый ресурс. Игра не падает: блок становится чёрно-фиолетовым кубом, а рецепта просто нет |
| каждый `.json` в jar разбирается | битый файл, который игра молча проглотит |
| в обоих языковых файлах есть оба ключа блоков каждого металла | сырой ключ перевода вместо названия |
| нет таблицы добычи `*_wall_torch.json` | непонимание раздела 6 |
| класс точки входа лежит внутри jar | jar, который Fabric не сможет запустить |
| `fabric.mod.json` проходит через `ModMetadataParser` самого fabric-loader; любое предупреждение роняет сборку | манифест, который игра отвергнет или на который пожалуется, — судит тот самый код, что читает его при запуске |

## 11. Отличия от ванильного факела

Известны и записаны, чтобы никому не пришлось открывать их заново:

| | Ванильный факел | Металлический факел |
|---|---|---|
| уровень света | 14 | 15 |
| пламя | частица `FLAME` | нет; цветные искры `DustParticleOptions` |
| настенный вариант, высота частиц | `y + 0.7 + 0.22` | с 1.1.1 так же (раньше `y + 0.7`). **Игрой не проверялось** |
| поведение с поршнем | `pushReaction(PushReaction.DESTROY)`: поршень сбивает факел предметом | с 1.1.1 так же. До этого флаг не ставился, действовало значение по умолчанию `NORMAL`, и поршень двигал бы факел. **Игрой не проверялось** |
| название настенного блока | скопировано с напольного (`overrideDescription`) | свой ключ перевода с тем же текстом |

## 12. Как добавить металл

1. **Проверь, нет ли такого факела в ваниле.** Именно так попались с медью: в 26.2 есть
   `minecraft:copper_torch`. Быстрая проверка — есть ли в клиентском jar файл
   `data/minecraft/loot_table/blocks/<имя>_torch.json`.
2. Добавь значение в `MetalTorch.java`: id, цвет `0xRRGGBB`, ингредиент.
3. Добавь ту же строку в `METALS` в `tools/resources.py`, с двумя отображаемыми названиями.
4. `python tools/resources.py write` — при расхождении двух списков он откажется работать.
5. Добавь id металла в список, который печатает `tools/SelfTest.java` (косметика: он лишь
   выводит ожидаемые пути).
6. `python build.py build`.

Убрать металл — то же самое наоборот; оставшиеся файлы генератор подчистит сам. Блоки
убранного металла исчезнут из существующих миров, как блоки любого удалённого мода.

## 13. Перенос на другую версию Minecraft

1. Поставь эту версию с Fabric и Fabric API, запусти один раз, направь `MC_PROFILE_DIR` на
   папку её профиля.
2. Поменяй `"minecraft"` в `resources/fabric.mod.json` (а также `"java"` и `--release` в
   `build.py`, если игра перешла на более новую Java).
3. `python build.py build` — и читай, что упало:
   * ошибки `javac` — переехал класс или метод. Обычные подозреваемые названы в этом
     документе: конструкторы `TorchBlock`, `codec()`, `DustParticleOptions`,
     `Properties.overrideLootTable`, `StandingAndWallBlockItem`, событие творческой вкладки
     в Fabric API;
   * проверка ссылок — ты компилируешь не против того клиента, о котором думаешь;
   * самотест — изменилось правило таблиц добычи; поправь путь в генераторе под то, что
     печатает тест.
4. Сверь форматы данных с новым клиентским jar: открой его собственные рецепт `torch`,
   таблицу добычи, достижение-разблокировку и `items/torch.json` и сравни с тем, что пишет
   генератор. Форматы данных меняются между версиями чаще, чем код.
5. Потом проверь игрой то, что не проверит никакая сборка: книгу рецептов, факел,
   сломанный на стене, частицы.
