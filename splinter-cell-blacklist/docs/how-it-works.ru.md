Это справочный документ — переходи сразу к нужному разделу.

Всё ниже получено из самого исполняемого файла `Blacklist_DX11_game.exe` (версия игры
`SC6_pcbranch_V2425.0_C603495`, Ubisoft Connect, 32 бита), из четырёх отчётов о вылете,
одного минидампа и одного полного дампа памяти упавшей сессии.

Все адреса — **виртуальные**. База образа `0x00400000`, релокации сняты, ASLR выключен,
поэтому адрес — одно и то же число в файле, в отладчике и в дампе. *Смещение ошибки*,
которое сообщает Windows, отсчитывается от базы образа:
`0x00422C5C` + `0x00400000` = `0x00822C5C`.

В `Blacklist_game.exe`, исполняемом файле под DirectX 9, тот же дефект лежит по другим
адресам; они приведены в разделе [Что именно меняет патч](#что-именно-меняет-патч).

## Вылет

```
Код исключения   0xC0000005  (нарушение доступа, чтение по адресу 0x00000000)
Смещение ошибки  0x00422C5C  ->  VA 0x00822C5C
Сбойный модуль   Blacklist_DX11_game.exe
WER bucket       22645ae42018a2885a5e49021f17ce34
```

У четырёх записанных вылетов совпадает всё, вплоть до смещения. Время от старта процесса
до вылета: **28:19, 27:04, 28:34, 28:35**. Одно и то же смещение четыре раза подряд
значит, что падает одна и та же инструкция, а не «где придётся».

Время работы взято из файла отчёта Windows Error Reporting `Report.wer`: две последние
группы его `AppSessionGuid` — это FILETIME старта процесса в порядке байтов памяти.

## Инструкция падения

`0x00822C30` — слот `[0]`, покадровый тик, таблицы виртуальных функций по адресу
`0x029BD504`. RTTI (Complete Object Locator по `0x02D80F24`) называет класс:

```
.?AVStateLoggingInToRdv@nsOnlineConnection@@
```

Это `nsOnlineConnection::StateLoggingInToRdv` — состояние входа в Quazal Rendez-Vous,
онлайн-сервис Ubisoft. Всего в автомате восемь состояний: `StateOffline`,
`StatePlatformNetworkStart`, `StateProxyDetection`, `StateSetLocale`,
`StateVerifyingServerVersion`, `StateLoggingInToRdv`, `StateOnline`,
`StateLoggingOutFromRdv`. Тик текущего состояния вызывается каждый кадр из автомата
`0x0081EA60` (сам вызов — `0x0081EBFF call eax`).

```asm
00822C30  push ebp                       ; начало функции, дальше только пролог:
          ...                            ; SEH-фрейм, стековый cookie, push esi/edi
00822C57  8B F1        mov  esi, ecx     ; esi = this
00822C59  8B 46 34     mov  eax, [esi+0x34]
00822C5C  80 38 00     cmp  byte ptr [eax], 0    ; <-- ЗДЕСЬ, eax == 0
00822C5F  0F 85 ...    jne  0x00822D96           ; «держатель пуст» -> штатный выход
00822C65  8B 40 1C     mov  eax, [eax+0x1C]
00822C68  85 C0        test eax, eax
00822C6A  0F 84 ...    je   0x00822D96           ; тот же штатный выход
```

Между входом в функцию и падающей инструкцией нет ни одной проверки `test` или `cmp`
над `eax`.

Запись об исключении и регистры из дампа:

```
ExceptionCode        0xC0000005
ExceptionAddress     0x00822C5C
ExceptionInformation [0, 0]          ; 0 = чтение, адрес обращения = 0
Eip = 0x00822C5C
Eax = 0x00000000     ; разыменованный указатель
Ecx = Esi = 0x489D7158   ; this
Edx = 0x029BD504     ; vtable StateLoggingInToRdv - тип объекта подтверждён в рантайме
```

Главное: `this` жив, `mov eax, [esi+0x34]` отработал без ошибки, а прочитанное значение —
**ровно ноль**, не мусор. Это закрывает версии «порча памяти», «use after free» и
«неинициализированный указатель» — каждая из них дала бы мусорный адрес, а не `0`.

## Почему ноль там — штатное значение

Поле `+0x34` хранит результат асинхронной операции (держатель `NetResult`). Остальной
код класса считает `NULL` обычным значением и проверяет его:

* слот `[7]` = `0x00780FB0` — это целиком `mov dword ptr [ecx+0x34], 0 / ret`; он
  вызывается при регистрации состояния;
* слот `[9]`, выход из состояния, = `0x00822DB0` начинается с
  `cmp dword ptr [ecx+0x34], 0 / je` — то есть **проверка на ноль тут есть**; хелпер
  освобождения `0x0080EAC0` на успешной ветке сам пишет ноль (`0x0080EB1E`);
* в отправке запроса `0x0086EEA0` ноль тоже предусмотрен (`0x0086F012`).

**Проверки нет только в слоте `[0]` — в тике.** Причём безопасный выход уже написан:
это `0x00822D96`, куда ведут обе штатные проверки той же функции.

Тот же незащищённый идиом есть у класса-близнеца `StateLoggingOutFromRdv` (слот `[0]` =
`0x00822F80`, разыменование на `0x00822FAC`, свой выход `0x0082308E`). Вылетов там не
наблюдалось.

Итого: тик — место, где игра падает, но ноль делается не в нём.

## Откуда берётся ноль

`StateLoggingInToRdv::Enter` (слот `[8]`, `0x0089AD00`) просит держатель у пула:

```asm
0089AEB0  mov  ecx, dword ptr [0x3383DF8]   ; пул; до вызова ecx не меняется
0089AEB6  mov  eax, dword ptr [ecx+0x18]
0089AEB9  cmp  byte ptr [eax+0x414], 0      ; предусловие
          ...
0089AEFB  call 0x00829450                   ; Alloc(this = пул)
          ...
0089AF09  mov  dword ptr [esi+0x34], eax    ; результат кладётся в this+0x34 без проверки
```

`Alloc` первым делом сравнивает счётчик свободных `[edi+0xF4]` с нулём; когда свободных
нет, он сразу уходит (`jbe`) на выход с `eax = 0`.

Полный дамп памяти (2 052 376 570 байт, `Memory64List`, 7062 диапазона, 1955 МБ памяти
процесса) показывает именно эту ситуацию:

```
объект состояния 0x489D7158
  +0x10 статус     = 0            ; не 4 (ошибка): Enter шёл по штатной ветке
  +0x14            = 0
  +0x30 владелец   = 0x48A1A1B0
  +0x34 держатель  = 0            ; NULL

пул = [0x03383DF8] = 0x489D3718
  +0xF4  свободных = 0            ; <-- вот оно
  +0x124 занятых   = 20
  [пул+0x18]+0x414 = 0x01         ; предусловие, которое Enter проверяет на 0x0089AEB9, выполнено
```

Статус `0` вместе с байтом предусловия `0x01` означает, что `Enter` дошёл до
`0x0089AEFB call 0x00829450`, а `Alloc` вернул `NULL`, потому что свободных не осталось.

Минидамп для этого бесполезен: куча в него не попадает, и ни объект состояния, ни пул
прочитать нечем. Нужен полный дамп (`MiniDumpWithFullMemory`).

## Как устроен пул

Внутри объекта пула — три списка одинаковой раскладки,
`{аллокатор 0x034DC108, тег, голова, хвост, счётчик}`, по `0x14` байт:

| Смещение | Голова | Хвост | Счётчик | Что это |
|---|---|---|---|---|
| `+0xE4` | `0x489D3804` | `0x489D3804` | **0** | свободные — голова равна хвосту и равна сентинелу внутри самого пула, то есть список пуст |
| `+0xFC` | `0x489D381C` | `0x489D381C` | 0 | освобождённые, ждут возврата в «свободные» — пуст |
| `+0x114` | `0x001C5418` | `0x001C4038` | **20** | занятые |

Список занятых обойдён целиком: кольцевой двусвязный, сентинел `0x489D3834`, ровно
20 узлов `{next, prev, obj}`, объекты `0x489D38A8` … `0x489D3BA0`. Число 20 задаётся при
создании пула (около `0x0088CFC5`, `mov [ebp-0x10], 0x14`); расти пул не умеет.

Жизненный цикл держателя:

* `Alloc` `0x00829450` берёт его из «свободных» и кладёт в «занятые»;
* `Free` `0x0080EAC0` забирает его из «занятых», кладёт в «освобождённые» и пишет ноль
  в поле владельца (`0x0080EB1E mov dword ptr [edi], 0`);
* `0x0083AEA0`, которую каждый апдейт зовут из `0x00887220`, перекладывает
  «освобождённые» обратно в «свободные».

То есть сам пул работает. Держатель возвращается тогда и только тогда, когда кто-то
вызвал `Free`.

Все двадцать занятых держателей выглядят одинаково:

```
[obj+0x00] дискриминатор = 0
[obj+0x14]               = 0            ; собственное поле держателя, его обнуляет Alloc
[obj+0x1C] указатель     = ненулевой    ; -> объект с vtable 0x029C5FDC
```

По RTTI объект за `+0x1C` — это `.?AUNetResultProxy@@`. Его код результата — поле
`+0x14`, которое отдаёт слот `[3]` vtable = `0x00803DC0`, `mov eax, [ecx+0x14] / ret`, —
у всех двадцати равен `0x80000001`. Тик считает такое значение неудачей: оно проходит
фильтр `test eax, 0xD0000000`, не совпадает ни с одним из особых кодов и приводит в
ветку, которая ставит статус состояния 4. Значит, это не двадцать операций, всё ещё
ждущих ответа. Это двадцать **завершённых** операций, чьи держатели никто не вернул.

## Дефект

`nsOnlineConnection::StateProxyDetection`:

| | |
|---|---|
| `Enter`, слот `[8]` = `0x00883BF0` | `mov ecx, [0x3383DF8] / call 0x829450 (Alloc) / mov [esi+0x34], eax` — берёт держатель из пула и кладёт в `this+0x34`, без проверки на ноль |
| `Exit`, слот `[9]` = `0x00775C40` | `ret 4` — **не делает вообще ничего** |

У состояния-близнеца `StatePlatformNetworkStart` (`Enter` `0x00837930` — тот же пул,
то же поле `+0x34`) в слоте `[9]` стоит настоящий `Exit`, по адресу `0x00822C10`:

```asm
00822C10  83 C1 34           add  ecx, 0x34            ; &this->m_holder
00822C13  51                 push ecx
00822C14  8B 0D F8 3D 38 03  mov  ecx, [0x03383DF8]    ; пул
00822C1A  E8 A1 BE FE FF     call 0x0080EAC0           ; Free
00822C1F  C2 04 00           ret  4
```

Поэтому каждый заход в `StateProxyDetection` безвозвратно тратит один слот из двадцати.
Когда пул пуст, `Alloc` отдаёт `NULL`, и первый же вызывающий его разыменовывает. Во
всех четырёх записанных вылетах этим вызывающим был тик `StateLoggingInToRdv`.

Двадцать слотов примерно за 28 минут — это один потерянный держатель каждые 85 секунд
или около того. Что именно задаёт этот ритм, до конца не прослежено. В дампе видно
двадцать одинаковых неудачных операций, что сходится с попыткой логина, которая
проваливается и повторяется по таймеру, каждый раз проходя через определение прокси.

## Доказательство из дампа памяти

Состояния лежат массивом внутри контроллера `0x48A1A1B0`, с шагом `0x40`:

| Адрес | Класс | `+0x34` (держатель) |
|---|---|---|
| `0x489D70D8` | `StatePlatformNetworkStart` | `0` — его `Exit` отработал и освободил держатель |
| `0x489D7118` | `StateProxyDetection` | `0x489D39C0` — **держит и не отпустит** |
| `0x489D7158` | `StateLoggingInToRdv` | `0` — здесь и упало |

`Free` обнуляет поле у владельца, поэтому ноль у `StatePlatformNetworkStart` доказывает,
что слот `[9]` **вызывается** и делает своё дело там, где в нём есть дело.

Из 20 занятых держателей 19 — сироты: во всей памяти процесса на них не указывает
ничто, кроме узла списка занятых самого пула. Двадцатый — тот, что сейчас у
`StateProxyDetection`.

## Что именно меняет патч

Один дворд в `.rdata`: слот `[9]` в vtable `StateProxyDetection` начинает указывать на
`Exit` состояния `StatePlatformNetworkStart`. Ни байта нового кода — функция уже есть в
исполняемом файле и уже делает эту работу для соседнего состояния.

| | `Blacklist_DX11_game.exe` | `Blacklist_game.exe` (DX9) |
|---|---|---|
| vtable `StateProxyDetection` | `0x029BD4AC` | `0x0297FEA4` |
| vtable `StatePlatformNetworkStart` | `0x029BD44C` | `0x0297FE44` |
| слот `[9]`, VA | `0x029BD4D0` | `0x0297FEC8` |
| слот `[9]`, смещение в файле | `0x025BB6D0` | `0x0257EAC8` |
| было | `40 5C 77 00` = `0x00775C40`, общий пустой стаб `ret 4` | `F0 3E A1 00` = `0x00A13EF0`, такой же стаб |
| стало | `10 2C 82 00` = `0x00822C10`, `Exit` у `StatePlatformNetworkStart` | `50 E0 AB 00` = `0x00ABE050` |
| глобал пула | `0x03383DF8` | `0x032B5DC8` |
| SHA-256 до | `c52b3d0927591e477424f389ff0b1314a300938e19ce61a7b0a7bc09f81c2c89` | `7fcd3a18d4dcc692719984b07268bd42764108e7df37049f1490f20929f9925d` |
| SHA-256 после | `4bb836c18c34135b73b682045825ad60c19f83888c5522b49e2ffd9c0eb8d7c1` | `690f721db38a36aa8c7b7c0fe99dd2a20b5078fa64a3418afac5ef75144ba635` |

В каждом файле от бэкапа отличаются ровно 3 байта: четвёртый байт дворда и до, и после
равен `00`.

`patches/603495/patch_pool_leak.json` — машиночитаемая копия этой таблицы. Программа её
не читает; это запись о том, как выглядит правильный результат на этой сборке.

## Как программа находит место

`patch_pool_leak.py` не хранит адресов. Обе vtable он находит через RTTI:

```
имя типа ".?AV<класс>@nsOnlineConnection@@"
  -> TypeDescriptor            (начинается за 8 байт до имени)
  -> Complete Object Locator   (его поле +12 указывает на TypeDescriptor, сигнатура равна 0)
  -> vtable                    (начинается сразу за двордом, который указывает на локатор)
```

Новое значение читается из слота `[9]` донора, а не берётся из константы. Поэтому тот же
скрипт патчит и исполняемый файл под DX9, где всё лежит в других местах, и переживает
обновление игры — пока классы называются так же.

Он отказывается писать, если:

* класс через RTTI не найден или найден не один раз — и имя типа, и локатор, и vtable
  должны быть единственными;
* `Exit` донора не имеет формы `83 C1 34 51 8B 0D <пул> E8 <rel32> C2 04 00`;
* `Enter` двух состояний ссылаются на разные пулы, либо этот пул не тот, что в `Exit`
  донора;
* функция, на которую слот `[9]` указывает сейчас, — не стаб `C2 04 00`: тогда состояние
  показывается как `UNKNOWN`, и файл остаётся нетронутым.

`apply` делает бэкап `<exe>.orig`, если его ещё нет, пишет дворд, сохраняет смещение,
оба значения и обе суммы SHA-256 в `<exe>.pool-leak-patch.json`, затем перечитывает файл
с диска и заново прогоняет весь анализ; любой итог, кроме `patched`, — ошибка. `revert`
возвращает 4 байта по этой записи, а если её нет — копирует бэкап поверх исполняемого
файла.

## Почему это безопасно

* **`Free` устойчива.** При `*pHolder == 0` она сразу выходит; если указателя нет в
  списке занятых — доходит до сентинела и возвращается, ничего не меняя. Даже вызов на
  поле, которое ни разу не заполнялось, безвреден.
* **Меняется ровно один дворд.** Проверено дизассемблером на настоящих файлах игры:
  остальные 15 слотов vtable байт в байт те же.
* **Донор и пациент совпадают.** `Enter` у обоих состояний делает одно и то же — тот же
  глобальный пул, то же поле `+0x34`, — и программа проверяет это перед записью.
* **Полностью обратимо.** `revert` возвращает исходный дворд, и SHA-256 снова равен
  оригинальному. Прогнано на копии: `apply` → повторный `apply` (ничего не делает) →
  `revert` → `c52b3d09…f81c2c89`.

## Аудит всех восьми состояний

После наложения проверены все классы автомата: `Enter` (слот `[8]`) и `Exit`
(слот `[9]`) разобраны целиком, с настоящими границами функций, и собраны все прямые
вызовы. Признак течи — `Enter` зовёт `Alloc` `0x00829450`, а `Exit` не зовёт `Free`
`0x0080EAC0`.

| Состояние | `Enter` берёт из пула | `Exit` освобождает | Итог |
|---|---|---|---|
| `StateLoggingInToRdv` | да | да (`0x00822DB0`) | в порядке |
| `StateLoggingOutFromRdv` | да | да (`0x008230B0`) | в порядке |
| `StatePlatformNetworkStart` | да | да (`0x00822C10`) | в порядке |
| `StateProxyDetection` | да | да (`0x00822C10`) — **после патча** | в порядке |
| `StateOffline` | нет | пустой стаб | безобидно |
| `StateVerifyingServerVersion` | нет | пустой стаб | безобидно |
| `StateOnline` | нет | — | безобидно |
| `StateSetLocale` | нет | — | безобидно |

Больше не течёт никто. Пустой `Exit` остаётся у двух состояний, но пул они не трогают
вообще, так что для них это правильно.

Аудит покрывает только этот автомат. Пул общий примерно для 106 мест онлайн-подсистемы,
и в принципе течь могла бы быть и снаружи автомата. Данных за это нет: в дампе
единственный держатель с живым владельцем принадлежал `StateProxyDetection`.

## Чего патч не делает

Он убирает течь. Проверок на ноль остальным пользователям пула он не добавляет: из 123
мест вызова `Alloc` минимум 105 передают этот же глобальный пул, и результат не
проверяет ни одно. Если пул когда-нибудь исчерпается по другой причине, игра упадёт
снова — просто в другом месте.

Два варианта рассмотрены и отброшены:

* **Проверка на ноль в падающем тике.** Она лечила бы одно место примерно из 106. К тому
  же с пустым пулом состояние логина тогда висело бы вечно: таймаута у состояний нет
  (слот `[1]` у всех восьми — стаб `0x00775BF0`, `fldz / ret`, то есть 0.0). Байты были
  рассчитаны, но в файлы игры не записывались, а после устранения течи пул больше не
  исчерпывается.
* **Пул побольше.** Это только отодвигает вылет.

Для справки: идиом `mov eax, [esi+0x34] / cmp byte ptr [eax], 0` встречается в `.text`
85 раз — это заинлайненный аксессор всего семейства `NetResult`. Патчить их все
бессмысленно и рискованно.

## Что было исключено

| Подозреваемый | Вердикт |
|---|---|
| Порча памяти, use after free, мусор в указателе | Опровергнуто замером: `Eax = 0`, `ExceptionInformation = [0, 0]`, `Edx` — валидная vtable, `this` жив. |
| Сторонние модули: оверлеи, античит, хуки, кряки, proxy-DLL | Исключено. Подпись исполняемого файла валидна (`CN=UBISOFT ENTERTAINMENT INC.`), подменных `dinput8` / `d3d9` / `dxgi` / `winmm` / `version` / `xinput` в папке игры нет, кадров сторонних модулей на стеке падения нет. Загруженные DLL оверлея и захвата между вылетами меняли версии; смещение ошибки не сдвинулось. |
| Видеодрайвер, TDR, WHEA, сон и пробуждение | Исключено: журнал Windows `System` вокруг каждого вылета пуст, графического кода на пути к падению нет. |
| DNS, файрвол, прокси, LSP | Исключено как причина: игру ничто не блокирует, а сделать поле `+0x34` невалидным сеть не может. |
| Сервис онлайн-конфигурации Ubisoft отвечает пустотой | Опровергнуто живой проверкой: на запрос с идентификатором, взятым из исполняемого файла, сервис отдаёт полную конфигурацию. |
| Давление на 32-битное адресное пространство, `RADAR_PRE_LEAK_WOW64` | Не участвует. Private commit был 1.49 ГБ, а исполняемый файл помечен `LARGE_ADDRESS_AWARE` (`Characteristics = 0x0123`), то есть его предел — 4 ГБ. Диагностика утечек Windows сработала на 3-й минуте, вылет случился на 28-й. |
| «Пул по конструкции не принимает объекты назад» | Опровергнуто: `0x0083AEA0` каждый апдейт возвращает освобождённые держатели в список свободных. Пул работает; не работает `Exit` одного состояния. |

## Не проверено

* **Игрой.** Патч стоит на обоих исполняемых файлах с 2026-09-04 и проверен в
  бинарнике. Сессия дольше 30 минут без вылета ещё не сыграна. Если вылет когда-нибудь
  вернётся при наложенном патче, полный дамп памяти отвечает на вопрос за минуту:
  прочитай указатель пула по `[0x03383DF8]` и его счётчик свободных по `+0xF4`. При
  работающем патче этот счётчик не должен падать до нуля.
* **Ритм в 85 секунд** — см. [Дефект](#дефект).
* **Автономный режим Ubisoft Connect** как обход. Скорее всего, автомат логина тогда не
  запускается. Не проверено; ценой будут мультиплеер и облачные сохранения.
* **Ключ командной строки `offline`.** Он существует: `0x00871BD7` взводит байт
  `[this+0x444]`, если в командной строке есть `offline`, а `Enter` у
  `StateLoggingInToRdv` читает его на `0x0089AD2E`. Ветка, в которую он уводит,
  `0x0089AD38`, даёт тот же результат `0x40000000` и тот же статус 4, что и обычный
  отказ логина, и до `Alloc` не доходит. Проходит ли автомат с этим ключом через
  определение прокси — и, значит, течёт ли по-прежнему — не проверялось.
* **Исполняемый файл под DX9 в игре.** Дефект и патч подтверждены в файле; вылетов на
  нём не записано, потому что все записанные сессии шли на DX11.
* **Мультиплеер и прочие сетевые функции.**

## Перенос на новую версию игры

Таблица под новую версию программе не нужна: если классы называются так же и три
предусловия выполняются, `apply` просто сработает. Что новой версии действительно нужно —
та же проверка, которую прошла эта.

```
python patch_pool_leak.py scan
```

печатает для каждого исполняемого файла vtable состояний `StateProxyDetection`,
`StatePlatformNetworkStart` и `StateLoggingInToRdv` и то, куда указывает слот `[9]`
каждого. На нетронутой сборке `603495`:

```
    StateProxyDetection          vtable 0x029BD4AC  slot[9] = 0x00775C40 (empty stub)
    StatePlatformNetworkStart    vtable 0x029BD44C  slot[9] = 0x00822C10
    StateLoggingInToRdv          vtable 0x029BD504  slot[9] = 0x00822DB0
```

Дальше:

1. `python patch_pool_leak.py check` должен показать `ORIGINAL (leak present)` для
   каждого исполняемого файла. Эта строка появляется, только когда выполнены все
   предусловия из раздела [Как программа находит место](#как-программа-находит-место).
2. `python patch_pool_leak.py apply`.
3. **Проверь дизассемблером**, что слот `[9]` у `StateProxyDetection` теперь содержит
   адрес `Exit` донора, а остальная vtable не тронута. «Скрипт отработал без ошибок»
   проверкой не считается.
4. Запиши значения в `patches/<сборка>/patch_pool_leak.json`, рядом с существующим.
   Номер сборки — это `main=` в разделе `[changelist]` файла `version.ini` в папке игры.
5. Бэкапы от прошлой версии (`*.exe.orig` и `*.exe.pool-leak-patch.json` рядом с
   исполняемыми файлами) удали **до** `apply`, иначе программа оставит протухший бэкап.

Если программа отказывается — значит разработчики изменили этот код. Начинай заново от
свежей записи о вылете: смещение ошибки → функция, в которой оно лежит → её vtable и имя
класса через RTTI → сравнение `Enter` и `Exit` у каждого состояния автомата. Состояние,
у которого `Enter` зовёт `Alloc`, а `Exit` ни разу не зовёт `Free`, и есть течь.
